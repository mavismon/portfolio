One design system,
from raw screens to working code

Horizon Stay — a UK holiday-home booking product, shipped on one system.

Horizon is a design system proven by shipping a guest web app, an iOS app and a staff back office on top of it. A crew of seven AI agents built, tested, shipped and documented it, while I made the design and system decisions.

01

Overview

The question

Can one design system carry a product from raw screens to working code without design and build drifting apart?

The starting point

Horizon Stay is a UK holiday-home booking product with a guest website, an iOS app and a staff back office. I started from a raw master file with about 130 guest screens and 82 back office screens, with no shared components and no naming.

What was going wrong
🎨

The same button, drawn many ways

Each screen had its own version of the same component, so one button looked different from one page to the next.

🛤️

Happy paths only

The designs showed the success case and left out the failure states that users run into.

🔗

No link to code

Nothing tied the Figma file to the code that had to match it.

My role

System architect, process designer, product designer and builder. I also directed a small crew of AI agents for the repeatable work.

I audited the raw file first (11 audits), then built tokens, then components, and only then the product. Each step left evidence that the next one could read.

One naming rule

Every token follows --{category}-{role or scale}. A Figma variable and its CSS property share one name, so a token reads the same in design and in code.

One build, three platforms

The same build writes CSS, iOS Swift and Android XML. Dark mode redeclares only the semantic colour tokens, so components never change.

03

The agent crew

Horizon is built, tested, shipped and documented by a small crew of seven AI agents, directed by me. Each agent has one lane and one job. The decisions stay with people: design sign-off, rulings on edge cases, the version tag and the npm publish.

The one rule

Agents never message each other. They hand work over through the Airtable registry, using evidence: a link, a test row or a commit. Status is a formula over that evidence, so no agent can type “done”.

Seven agents, one lane each
🛠️

Engineer

Builds or repairs one component from one Figma node, and owns the token pipeline. Never tests its own work.

🧪

QA

Tests every variant and state against Figma, and writes Passed or Failed with a fix an engineer can act on. Never fixes.

🚢

DevOps

Merges and deploys a component once QA has passed it. Never changes anything after QA.

📚

Doc generator

Writes each component's intent file and builds the docs site. Never invents intent content.

🏷️

Release

Runs a release end to end, from preflight to a publish dry run. It proposes the version and never decides it.

🔍

PM

Audits the whole registry from outside and reports every row where evidence and status disagree. Read-only on purpose.

🎛️

Token runner

Runs the token build and reports the raw output. No analysis, no editing.

Nine shared skills

Each skill is a playbook the agents read before they work, so two agents never invent two procedures for the same job.

registry build test finding-format security-check component-intent astro-page release-review sweep
🔎

The release review checks seven gates and six intent-file checks before a component's name goes into a public version. Its own advice: “Expect Blocked on a first run. A review that passes everything first time isn't reading.”

What surprised me

  • Spawned agents cannot open a browser, so I do the “watch it render” step myself and write those links.
  • The engineer refused to write a staging link on my say-so. It was right: only whoever opened the page can vouch for it.

What stays with me

A decisions.md file holds my rulings on findings that aren't defects, and only I write in it. Sign-off, the version tag and the npm publish stay with me, so no agent ships an irreversible step on its own.

05

From code to published

A finished component moves out in a fixed order. Each step is recorded in the registry, and a person makes the final call on release.

Tokens build→Components bundle into three entry points→Staging on Storybook→QA passes→Production Storybook→Astro docs site→Reviewed release, npm

Staging and production

Storybook runs on Vercel, and every state is a story and a test row. Production only follows a QA pass, and a security check scans the build for secrets first.

Docs and release

The docs are an Astro Starlight site with one page per component, each linked back into the registry. Every release is reviewed first, then I tag the version and publish to npm.

06

Using Horizon in the product

A design system proves itself in a real product. These are the rules I followed when I built with Horizon.

  1. Import tokens, then package styles, then the app reset, in that order.
  2. Audit and map every Figma instance to an export before building.
  3. Use a component exactly as Figma shows it. No restyling, no wrapper.
  4. Style with tokens only. No hardcoded values and no Tailwind.
  5. Build gaps locally from tokens, and record each one for the system owner.

What I'd tell my past self

  1. Audit before you build.
  2. Design the unhappy paths. Trust is won or lost there.
  3. Make status come from evidence.
  4. Separate the builder from the checker.
  5. Keep a human on the irreversible steps.
